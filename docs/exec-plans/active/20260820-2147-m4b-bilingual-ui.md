## Purpose / Big Picture

Today every word the app says is a Polish string typed into a component, a
screen or a helper. Someone whose phone is set to English opens Peeers and gets
Polish. There is no way to add a second language without editing thirty files,
and no way for the "Wygląd" settings screen of M7 to offer a language at all.

After this change the app speaks Polish and English. Which one it speaks is
decided once at startup from the phone's own language list: a phone that asks
for Polish gets Polish, and every other phone gets English. Nothing in the UI
lets you switch — that arrives later, in the settings screen of M7, and this
plan leaves the seam it will plug into.

You can see it working without writing code: with the app running, change the
iPhone Simulator's language in Settings to English, reopen Peeers, and the tab
bar reads Space / Shopping / Notes / You instead of Przestrzeń / Zakupy /
Notatki / Ty. Every screen built so far follows: the list index, the list
itself, the item sheet, the "Co tworzymy" sheet, the activity sentences on the
cards ("Kuba added 3 items · yesterday") and the dates under them.

There is a second reason to do this now rather than at the end. M4.5 to M4.8
and everything from M5 onward will write new copy. Doing the extraction now
means that copy is written into the message files from the start, instead of
being extracted a second time later.

## Assumptions

A1. Two languages only, `pl` and `en`, chosen by language code alone. Region is
ignored: `pl-PL` and `pl` are the same thing here, and `en-GB` and `en-US` are
too. There are no region-specific strings in this app.

A2. English is the fallback for every language that is not Polish, which is what
the repo owner asked for. A phone set to German gets English.

A3. The language is resolved once, when the app starts. Nothing persists a
choice, because nothing can make one yet. If the phone's language changes while
the app is in the background, the change takes effect at the next launch.

A4. English is **authored**, not measured. The Polish copy is verbatim from the
mockups and stays the reference for layout; if an English string turns out to
be too long for its row, the English string is what gets shortened.

A5. English dates read "12 August", not "August 12" — same word order as the
Polish "12 sierpnia", so a card that fits in one language fits in the other. The
month heading of mockup 41 becomes "AUGUST".

A6. The Polish gendered verb forms ("dopisał(-a)", "usunął(-ęła)") have no
English counterpart and become plain past tense ("added", "removed"). English
sentences are shorter than Polish ones everywhere, never longer, so nothing
that fits today stops fitting.

A7. `src/db/seed.ts` stays Polish. It is development data — the Przestrzeń drawn
in the mockups — not UI copy, and translating "Mleko owsiane" would make the
seeded database stop matching the drawings it was built from. See Q3.

A8. The two development-only routes, `src/app/gallery.tsx` and
`src/app/db.tsx`, are not translated. They exist to check components and the
data layer against the mockups and are never shown to a user. See Q3.

A9. The repo owner has an iPhone 17 simulator booted and Metro running on port
8081. No Android emulator is running at the time of writing, so Android
verification happens when one is up. **Do not start either device.**

## Surprises & Discoveries

- Observation: Hermes does not implement `Intl.PluralRules`, which i18next needs
  for anything beyond English's one/other split. Without it Polish silently
  falls back to two forms and "5 pozycji" renders as "5 pozycja".
  Evidence: i18next's own plural documentation, at
  https://www.i18next.com/translation-function/plurals — "In environments
  without Intl.PluralRules support you need to polyfill it (notably React
  Native: the Hermes engine still does not implement Intl.PluralRules)". Since
  i18next v24 there is no built-in fallback. React Native ships Hermes v0.17.0
  here (`node_modules/react-native/sdks/.hermesversion`).

- Observation: both compile-time safety nets work, and the first one even
  suggests the right key. Checked by deliberately breaking each, then undoing
  it. A key that does not exist:

      src/i18n/tmpcheck.ts(2,27): error TS2345: Argument of type
      '["tabs.spac"]' is not assignable to parameter of type '[key:
      TemplateStringsArray | "app.done" | ... 25 more ... ]'.
        Did you mean '"tabs.space"'?

  And `messages/pl.json` missing a key `messages/en.json` has:

      src/i18n/index.ts(38,7): error TS2322: Type '{ ... tabs: { space: string;
      lists: string; notes: string; you: string; }; ... }' is not assignable to
      type '{ ... tabs: { space: string; lists: string; notes: string; you:
      string; create: string; }; ... }'.
        Property '"create"' is missing in type ... but required in type ...

- Observation: `npm install` and `npx expo install` rewrite `package.json` and
  `package-lock.json` with two-space indentation, and both files are
  tab-indented in this repo. The result is a 20 000-line diff that hides the
  four lines that actually changed.
  Evidence: `git diff --stat` immediately after the installs read
  `package-lock.json | 20660 ++++----`, and after re-serialising both files with
  tab indentation it read `102 ++++`. Re-indent after any install here. Note
  that `app.json` is the exception: it is two-space indented and npm leaves it
  alone.

- Observation: `pod install` fails in a non-interactive shell with no `LANG`
  set — "Unicode Normalization not appropriate for ASCII-8BIT" — and
  `expo run:ios` reports the failure while still exiting 0, so a script cannot
  tell it went wrong from the exit code alone.
  Evidence: the first `npx expo run:ios --no-bundler` ended with
  "Something went wrong running `pod install`" and `[exited with code 0]`.
  `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 npx expo run:ios` works. This is a
  property of the shell, not of the repo — the repo owner's own terminal has a
  UTF-8 locale — but anything driving the build from a script needs it.

- Observation: the other language can be checked without touching the device's
  settings, by passing iOS's `-AppleLanguages` launch argument. It sets
  `NSLocale.preferredLanguages` for that process only, which is exactly what
  `expo-localization` reads, so no reboot and no temporary `lng` override are
  needed. The development client needs the deep link afterwards, delivered to
  the already-running process so it keeps the launch argument:

      xcrun simctl terminate booted com.s.walach.peeers
      xcrun simctl launch booted com.s.walach.peeers -AppleLanguages '(en)'
      xcrun simctl openurl booted "exp+peeers://expo-development-client/?url=http%3A%2F%2F192.168.0.52%3A8081"

  Relaunching without the argument puts the device back as it was. This is
  better than the temporary `lng: 'en'` edit the plan first suggested, because
  it exercises the real detection path rather than bypassing it — the Validation
  section now says so.

- Observation: the Android build failed twice for reasons that had nothing to do
  with this plan, and the repository's own documentation was part of why. README
  said the JDK is "pinned for every Gradle build" in `~/.gradle/gradle.properties`
  via `org.gradle.java.home`, which is only half true: that property names the
  JDK Gradle *builds* with, and cannot name the one Gradle *starts* on, because
  the wrapper has to be running before it can read a Gradle property. With
  `JAVA_HOME` unset and Homebrew's openjdk keg-only, the wrapper fell through to
  `/usr/bin/java`, the macOS stub:

      The operation couldn't be completed. Unable to locate a Java Runtime.

  Setting `JAVA_HOME` for one invocation showed both mechanisms side by side and
  proved the pin itself was fine:

      Launcher JVM:  17.0.20.1 (Homebrew 17.0.20.1+0)
      Daemon JVM:    /opt/homebrew/opt/openjdk@17/... (from org.gradle.java.home)

  `ANDROID_HOME` was missing for the same reason — the shell had no Android
  environment at all — and produced "SDK location not found" next. Both are now
  in `~/.zprofile` and documented in README. Note the second error suggests
  writing `sdk.dir` into `android/local.properties`; that is the wrong fix here,
  because `android/` is generated by `expo prebuild` and discarded on the next
  run — the same reason the JDK pin lives in the user's Gradle properties.

- Observation: Android has an equivalent of the iOS `-AppleLanguages` trick, and
  it is better, because it survives a restart. From API 33 the per-app language
  can be set from the shell, and `expo-localization` reads it —
  `LocaleListCompat.getDefault()` in its `LocalizationModule.kt` picks it up:

      adb shell cmd locale set-app-locales com.s.walach.peeers --locales pl
      adb shell am force-stop com.s.walach.peeers
      adb shell am start -a android.intent.action.VIEW -d "exp+peeers://expo-development-client/?url=http%3A%2F%2F192.168.0.52%3A8081"

  Clear it afterwards with `--locales ""` so the emulator is left as it was. The
  emulator's own locale is `en-US`, so Polish is the override there and English
  is the default — the mirror image of the iPhone, which is useful: between the
  two devices both the match and the fallback are exercised without either being
  reconfigured.

- Observation: the polyfill was needed, and the proof is one line. Read off the
  Pixel 6 emulator with a temporary probe, `Intl.PluralRules.polyfill` came back
  `true` — meaning `intl-pluralrules` found nothing to defer to and installed
  itself, exactly as the guard predicts on Hermes. The forms are then right,
  including the three that a two-form implementation gets wrong:

      [plural] polyfill= true
      [plural] lang= 'pl'
      1  -> '1 pozycję'   / '1 pozycja'
      2  -> '2 pozycje'   / '2 pozycje'
      3  -> '3 pozycje'   / '3 pozycje'
      5  -> '5 pozycji'   / '5 pozycji'
      12 -> '12 pozycji'  / '12 pozycji'
      13 -> '13 pozycji'  / '13 pozycji'
      14 -> '14 pozycji'  / '14 pozycji'
      22 -> '22 pozycje'  / '22 pozycje'
      0  -> '0 pozycji'   / '0 pozycji'

  The left column is `activity.items`, the right `list.itemCount`. They differ
  at 1 and nowhere else — "1 pozycję" against "1 pozycja" — which is the whole
  argument for keeping them as two keys rather than one.

- Observation: a `console.log` at module scope produces a LogBox error, "Can't
  perform a React state update on a component that hasn't mounted yet", whose
  stack points at `LogBoxData.js` and `ExpoRoot.js` rather than at any app code.
  The likely reading is that LogBox is updating its own state before it has
  mounted, since the log runs during the first module evaluation. It appeared
  with the temporary plural probe above and went away when the probe did; a cold
  start without it is clean, and so is editing a message file with the app
  running. Worth knowing before mistaking it for a defect in the i18n setup.

## Decision Log

- Decision: use **i18next** with **react-i18next**, rather than `i18n-js`,
  `lingui` or `react-intl`.
  Rationale: four things had to be true at once. Messages must live in plain
  JSON files, which the repo owner asked for and which rules out `lingui`'s
  compiled catalogs and its Babel macro. Polish needs three plural forms from
  CLDR rules, which `i18n-js` only gets through a hand-written pluralizer — the
  very thing `src/lib/plural.ts` is and which this plan deletes. Translation
  must work **outside React**, because `src/lib/eventText.ts` and
  `src/lib/time.ts` are plain functions and not components; i18next's instance
  method `i18n.t` does that, while a hooks-only API would force a translator
  argument through every call site. And the keys must be type-checked, because
  `npx tsc --noEmit` is the only automated gate this repo has; i18next generates
  key types from the message file. `react-i18next` adds the `useTranslation()`
  hook, which re-renders subscribed components when the language changes — the
  seam M7's settings screen needs.
  Date/Author: 2026-08-20, Claude (planning).

- Decision: polyfill `Intl.PluralRules` with **`intl-pluralrules`** (the
  package i18next's own plural documentation links to), imported once for its
  side effect.
  Rationale: see the Surprises entry for why a polyfill is needed at all. This
  plan first named `@formatjs/intl-pluralrules`, and the repo owner pointed at
  the i18next documentation, which links to eemeli's `intl-pluralrules`
  instead. It is the better fit here on three counts: it has no dependencies of
  its own, where the formatjs package pulls in `@formatjs/bigdecimal` and
  `@formatjs/intl-localematcher`; it carries every CLDR locale in the package,
  about 7 kB minified and gzipped, so there is no per-locale data import to
  remember to add when a third language arrives; and it is one import line
  rather than three.
  The one thing given up is `polyfill-force`. `intl-pluralrules` installs
  itself conditionally — but the condition is not a bare existence check, which
  is what would have been worrying. Reading its entry point (quoted under
  Artifacts), it replaces `Intl.PluralRules` unless the engine has it *and*
  that implementation has `selectRange` *and* it reports support for `en`, `es`,
  `ru` and `zh`. A partial engine implementation is therefore still replaced,
  and a complete one is correct to defer to. It also leaves a marker,
  `Intl.PluralRules.polyfill === true`, which the validation section uses to
  check at runtime that it actually loaded. If a future engine ever passes the
  guard while still getting Polish wrong, the escape hatch is the ponyfill —
  see Idempotence and Recovery.
  The alternative of keeping `src/lib/plural.ts` for Polish and using i18next
  only for English was rejected outright: it would leave two plural systems in
  the codebase disagreeing about the same numbers.
  Date/Author: 2026-08-20 (planning), revised 2026-08-21 after the repo owner's
  reading of the i18next docs.

- Decision: the message files live in `messages/` at the repository root, as
  `messages/pl.json` and `messages/en.json`, reached from code through a new
  tsconfig path `@/messages/*`.
  Rationale: the repo owner asked for a `messages` folder. The path alias
  mirrors the `@/assets/*` entry that already exists in `tsconfig.json`, so the
  import reads `@/messages/pl.json` the way asset imports read `@/assets/...`.
  Metro picks tsconfig paths up automatically in Expo SDK 50 and later, but only
  reads the file at startup — Metro has to be restarted after the alias is
  added.
  Date/Author: 2026-08-20, Claude (planning).

- Decision: Polish stays verbatim from the mockups; English is authored by
  whoever writes the feature. AGENTS.md rule 3 is amended to say so.
  Rationale: rule 3 currently reads "UI copy is Polish and is taken verbatim
  from the mockups, never translated by hand", which forbids exactly what this
  plan does. The rule's intent — that nobody paraphrases the drawings — is kept
  by making Polish the side that must match them, and by saying that Polish is
  the reference for layout so an over-long English string is the one that gets
  cut. The Polish domain terms stay Polish in documentation and code comments,
  unchanged.
  Date/Author: 2026-08-20, Claude (planning).

- Decision: month names, weekday names and the relative words ("wczoraj",
  "dziś") live in the message files, not in `Intl.DateTimeFormat`.
  Rationale: Hermes can format dates, but Polish weekdays in this app carry
  their preposition and it is not always the same word — "we wtorek", not "w
  wtorek" — and no date formatter produces that. Having half the calendar come
  from the engine and half from a message file would be worse than either. The
  message files are also deterministic offline and do not depend on which ICU
  data the OS shipped.
  Date/Author: 2026-08-20, Claude (planning).

- Decision: modules in `src/lib/` read the active language from `src/i18n`
  directly, instead of taking a translator as an argument.
  Rationale: `shortWhen(said.at)` is called inline in JSX in several places and
  threading a `t` through each call would be noise. The cost is that those
  functions are no longer pure with respect to the language — the same
  consequence `new Date()` already has for the clock. The practical consequence
  is a rule, written into AGENTS.md: **a component that renders text produced by
  a `src/lib` helper must call `useTranslation()` itself**, so react-i18next
  re-renders it when the language changes. This does not matter until M7 adds a
  switcher, and it costs nothing to obey now.
  Date/Author: 2026-08-20, Claude (planning).

- Decision: delete `src/lib/plural.ts`.
  Rationale: every one of its five call sites becomes a plural key. Leaving it
  would leave a second, hand-written implementation of Polish plural rules for
  the next person to reach for. Its one piece of hard-won knowledge, that 12-14
  take the "many" form rather than the "few" form that 2-4 take, is what CLDR
  encodes, and the plan's validation checks that specific case.
  Date/Author: 2026-08-20, Claude (planning).

- Decision: `messages/en.json` is the type source, and `messages/pl.json` is
  checked against it by an assignment in `src/i18n/index.ts`.
  Rationale: i18next derives its key types from one resource. Taking English —
  the fallback language — means a key that only exists in Polish is a type
  error at the call site. The reverse gap, a key English has and Polish lacks,
  would otherwise be invisible until it rendered in English on a Polish phone;
  the assignment `const _plCoversEn: typeof en = pl` fails `npx tsc --noEmit`
  when that happens. Extra Polish-only keys — the `_few` and `_many` plural
  forms English does not have — are allowed, because excess-property checking
  does not apply when assigning from a variable.
  Date/Author: 2026-08-20, Claude (planning).

- Decision: replace the hard-coded `headerBackTitle: 'Mieszkanie 14'` in
  `src/app/_layout.tsx` with the Przestrzeń's actual name, read in
  `src/app/list/[id]/index.tsx`.
  Rationale: it is a Polish string typed into a component, which is what this
  plan exists to remove, and it is also simply wrong — it is one seeded
  Przestrzeń's name standing in for whichever one the list belongs to. It is
  not a translation, so it becomes data rather than a key.

## Context and Orientation

**What this repository is.** Peeers is an Expo SDK 57 app in TypeScript, using
expo-router for file-based routing: a file under `src/app/` is a screen, and its
path is its URL. `src/app/(tabs)/lists.tsx` is the Zakupy tab,
`src/app/list/[id]/index.tsx` is one shopping list, `src/app/item/[id].tsx` is
the bottom sheet showing one item. Design values come from `src/theme/tokens.ts`
through the `useTheme()` hook and are never typed into a component. The database
is SQLite through Drizzle ORM under `src/db/`, and `src/lib/` holds plain
helper functions with no React and no database in them.

**What "message file" means here.** A JSON file mapping a key to a sentence.
`messages/pl.json` holds the Polish sentences and `messages/en.json` the
English ones, with identical keys. Code names the key —
`t('list.toBuy')` — and the library returns whichever language is active.

**What "interpolation" means here.** A message can carry a slot written
`{{name}}`, filled at render: `t('item.removeTitle', { name: 'Chipsy' })` with
the Polish message `Usunąć „{{name}}"?` produces `Usunąć „Chipsy"?`.

**What "plural key" means here.** Polish picks between three forms of a counted
noun, and which one depends on the number in a way that is not "one versus many":
1 takes "pozycja", 2-4 take "pozycje", 5 and up take "pozycji" — except 12, 13
and 14, which take the 5-and-up form. The library encodes this and picks the form
from the number, if the message file supplies all of them. A plural key is
therefore several JSON entries sharing a base name and differing by suffix:
`itemCount_one`, `itemCount_few`, `itemCount_many`, `itemCount_other`. The code
names only the base: `t('list.itemCount', { count: 5 })`. English supplies
`_one` and `_other` and gets "5 items". The `_other` form exists in Polish for
fractions, which this app never counts; it is filled with the same text as
`_many` so the library never has to fall back.

**Which routes are affected**, by full path:

    src/app/_layout.tsx                the two headerBackTitle strings
    src/app/(tabs)/_layout.tsx         the four tab titles
    src/app/(tabs)/index.tsx           the Feed stub
    src/app/(tabs)/lists.tsx           the Zakupy tab, mockup 35
    src/app/(tabs)/notes.tsx           the Notes stub
    src/app/(tabs)/profile.tsx         the Profile stub
    src/app/item/[id].tsx              the item sheet, mockup 28
    src/app/list/[id]/index.tsx        one list, mockups 07, 39, 15, 08
    src/app/new.tsx                    the "Co tworzymy" sheet, mockup 05
    src/app/note/[id].tsx              the Note stub
    src/components/TabBar.tsx          the "Utwórz" accessibility label

**Which mockups specify this copy.** `05` (the create sheet), `07` and its dark
counterpart `39` (a list), `08` (typing an item), `15` (an empty list), `28`
(the item sheet), `35` (the list index), `41` (the archive), `25` (the change

**Which theme tokens are used.** None are added or changed. This plan moves text

**Deliberately out of scope.** Nothing in this plan appears under

**Create `src/i18n/index.ts`.** This is the whole of the setup:

    /**
     * The app's two languages.
     *
     * Which one is active is decided once, here, at startup: the phone's own
     * ordered language list is scanned and the first supported entry wins.
     * Anything that is neither Polish nor English gets English. Nothing lets
     * the user choose yet — that is M7's settings screen, which will call
     * `setLanguage` and persist the answer.
     *
     * Hermes, the JavaScript engine both platforms run, does not implement
     * `Intl.PluralRules`, and i18next has needed it since v24 for anything
     * beyond English's one/other split. Without the import below, Polish
     * silently loses its `_few` and `_many` forms and "5 pozycji" renders as
     * "5 pozycja" — wrong text, not an error.
     *
     * The import has no bindings; it is here for its side effect. It carries
     * every CLDR locale, so adding a third language needs nothing here, and it
     * steps aside only for an engine that already has a complete
     * implementation. `Intl.PluralRules.polyfill` is `true` when it loaded.
     */
    import 'intl-pluralrules'

    import { getLocales } from 'expo-localization'
    import i18n from 'i18next'
    import { initReactI18next } from 'react-i18next'

    import en from '@/messages/en.json'
    import pl from '@/messages/pl.json'

    /*
     * English is the type source, so `t('does.not.exist')` fails
     * `npx tsc --noEmit`. This assignment covers the other direction: it stops
     * compiling when pl.json is missing a key en.json has. Polish-only keys —
     * the `_few` and `_many` plural forms English has no use for — are fine,
     * because assigning from a variable does not check for excess properties.
     */
    const _plCoversEn: typeof en = pl
    void _plCoversEn

    export const languages = ['pl', 'en'] as const
    export type Language = (typeof languages)[number]

    /** English for every phone that did not ask for Polish. */
    export const fallbackLanguage: Language = 'en'

    /**
     * The phone's first supported language.
     *
     * `getLocales()` returns the whole preference list, not one entry, so a
     * phone set to German first and Polish second gets Polish rather than the
     * fallback.
     */
    export function deviceLanguage(): Language {
      for (const locale of getLocales()) {
        const code = locale.languageCode
        if (code && (languages as readonly string[]).includes(code)) {
          return code as Language
        }
      }

      return fallbackLanguage
    }

    i18n.use(initReactI18next).init({
      resources: { en: { translation: en }, pl: { translation: pl } },
      lng: deviceLanguage(),
      fallbackLng: fallbackLanguage,
      // React escapes what it renders; i18next escaping on top of it would
      // turn a name containing an apostrophe into "Ola&#39;s".
      interpolation: { escapeValue: false },
      returnNull: false,
    })

    /** M7's settings screen calls this. Nothing else should. */
    export function setLanguage(language: Language): Promise<unknown> {
      return i18n.changeLanguage(language)
    }

    export default i18n

## Idempotence and Recovery

Every step is safe to repeat. The npm installs are idempotent; re-running them
re-resolves the same versions. Editing a message file and reloading is
non-destructive, and nothing in this plan touches `src/db/schema.ts`, so no
migration is generated and no database is rewritten — the seeded Przestrzeń
survives the whole plan untouched.

The single risky moment is the native rebuild in Milestone 1: between installing
`expo-localization` and finishing `npm run ios` / `npm run android`, the
installed development builds do not have the new native module and the app fails
at startup on `getLocales()`. Recovery is to finish the rebuild. To back out
entirely, `npm uninstall expo-localization i18next react-i18next
intl-pluralrules`, remove `"expo-localization"` from `app.json`,
`git checkout` the touched files and rebuild once more.

If `Intl.PluralRules.polyfill` is not `true` at startup and Polish plurals are
wrong anyway — an engine that satisfies the guard quoted under Artifacts but
still mishandles `pl` — the same package ships a ponyfill that can be installed
by hand, which is the `polyfill-force` behaviour this plan gave up:

    import PluralRules from 'intl-pluralrules/plural-rules'
    // eslint-disable-next-line
    ;(Intl as { PluralRules: unknown }).PluralRules = PluralRules

Do this only with evidence that the guard let a broken implementation through;
record it in Surprises & Discoveries with the failing number and form.

If the language ever comes out wrong and it is not obvious why, log
`getLocales()` and `i18n.language` at startup: the first is what the phone asked
for, the second is what was resolved, and the gap between them is the whole of
the detection logic.

## Artifacts and Notes

The polyfill decision rests on this, from i18next's own plural documentation at
https://www.i18next.com/translation-function/plurals:

    In environments without Intl.PluralRules support you need to polyfill it
    (notably React Native: the Hermes engine still does not implement
    Intl.PluralRules).

The engine version this repo ships, from
`node_modules/react-native/sdks/.hermesversion`:

    hermes-v0.17.0

`intl-pluralrules` installs itself conditionally, and this is the whole of the
condition — the entry point of `intl-pluralrules@2.0.1`, lightly trimmed. It
matters because it is what makes a conditional polyfill safe here: the engine
has to have a complete implementation, not merely a property called
`PluralRules`.

    if (typeof Intl === 'undefined') {
      global.Intl = { PluralRules: PluralRules__default["default"] }
      PluralRules__default["default"].polyfill = true
    } else if (!Intl.PluralRules || !Intl.PluralRules.prototype.selectRange) {
      Intl.PluralRules = PluralRules__default["default"]
      PluralRules__default["default"].polyfill = true
    } else {
      var test = ['en', 'es', 'ru', 'zh']
      var supported = Intl.PluralRules.supportedLocalesOf(test)
      if (supported.length < test.length) {
        Intl.PluralRules = PluralRules__default["default"]
        PluralRules__default["default"].polyfill = true
      }
    }

On Hermes the second branch fires, because there is no `Intl.PluralRules` at
all. The `polyfill = true` marker each branch sets is what the validation
section checks.

Milestone 1, on the booted iPhone 17. The simulator's language list reads

        "pl-PL",

With the app launched normally, the feed stub and the tab bar read

## Interfaces and Dependencies

New dependencies, and why each one is there:

    expo-localization ~57.0.1   the phone's ordered language list
    i18next ^26.4.0             message lookup, interpolation, plurals
    react-i18next ^17.0.12      useTranslation(), re-render on change
    intl-pluralrules ^2.0.1     Intl.PluralRules, which Hermes lacks

`intl-pluralrules` has no dependencies of its own; the other three bring
nothing surprising. Nothing here is imported anywhere except `src/i18n/`, which
is the point of having that directory: the rest of the codebase depends on
`@/i18n` and on `useTranslation`, not on which library is behind them.

What must exist at the end, in `src/i18n/index.ts`:

    export const languages: readonly ['pl', 'en']
    export type Language = 'pl' | 'en'
    export const fallbackLanguage: Language
    export function deviceLanguage(): Language
    export function setLanguage(language: Language): Promise<unknown>
    export default i18n   // the initialised i18next instance

And the two conventions every later milestone follows. In a component:

    const { t } = useTranslation()
    <Text>{t('list.toBuy')}</Text>

Outside React — `src/lib/`, and module-level helpers in a screen file:

    import i18n from '@/i18n'
    i18n.t('activity.items', { count })

A component that renders text a `src/lib` helper produced calls
`useTranslation()` even if it does not use `t` directly, so react-i18next
re-renders it when M7's settings screen changes the language.
